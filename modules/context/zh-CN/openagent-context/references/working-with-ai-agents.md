# 和 AI agent 一起干活：踩过的坑

这一页记的是一名维护者带着 AI agent 做长项目时踩过的坑，以及现在怎么做。规则本身在[契约模板](contract-template.md)和[决策日志模板](decision-log-template.md)里，这里不再重复；这里只写那些规则是从哪来的，和放不进契约的做法。把活交给别的 agent CLI 的经验，在 delegate 模块里。

每条的写法：**坑**是当时出了什么事，**现在**是之后怎么做。

## 1. 契约怎么保持短

- **契约被状态行撑爆。** 坑：agent 每做完一件事就「顺手更新一下文档」，进度、状态行、历史都写进了契约，契约越来越长，真正的规则被挤出上下文。提醒拦不住。现在：契约里不写状态行，只写进度放在哪；定一个行数上限，过了就删，不再加；可以用 hook 在每次改完后报告行数。Codex 读 `AGENTS.md` 只读到 32 KiB。
- **旧版不留在契约里。** 坑：旧契约里堆着阶段计划、状态表和旧技术栈，重写时不知道该不该留。现在：删干净，契约末尾写一句旧版在哪个提交，要考古时用 `git show <提交>:CLAUDE.md` 看。
- **做顺了的流程不写进契约。** 坑：一套操作步骤写进契约，契约就长一截。现在：一次做顺了的流程，在任务末尾提议做成 skill 或模板，契约里最多留一行指向。
- **记忆索引一行只写钩子。** 坑：索引本该一条一行，结果某一行被不断追加进度，写成了几千字的流水账，每个会话都要整个读进上下文。现在：索引一行只写「是什么、去哪看」，进度写进那条记忆自己的文件或计划文档。

## 2. 规则怎么写才有人守

- **规则不标出处。** 坑：agent 分不清哪条是硬要求、哪条是以前的建议，要么死守过时的建议，要么随手变通硬要求。现在：每条规则标出处（`[owner]`、`[agreed]`、`[incident]`、`[D0xx]`，含义见契约模板），要变通之前先查它为什么存在。
- **人的原话没进契约。** 坑：聊天里反复说过的要求从没写进契约，每个新会话都要再说一遍。现在：重建契约时，只从历史对话记录里抽人亲手打的消息，不从 agent 的转述里抽。
- **推荐被记成人的决定。** 坑：人大多数时候点选的是 agent 的推荐项，记录里却写成人自己的决定，日后翻记录分不清是谁的判断。现在：记成「agent 建议、人同意」；原话要紧时直接引用。
- **只写在文字里的规则。** 坑：第一次碍事时就被忘掉。现在：绝不能破的那几条，每条配一个破了就失败的东西：测试、lint 规则或 CI 任务。检查器先证明自己：故意改坏一处，看它报错，再信它。

## 3. 什么算做完

- **测试全绿，真跑才出问题。** 坑：单测全过，真调用模型时才暴露问题。现在：做完等于真实跑过；涉及模型调用的改动，用真实项目真调一次。
- **测试碰了真实配置。** 坑：测试和它启动的子进程写进了开发者自己的配置目录。现在：测试和它起的每个进程都指向临时文件夹。
- **同一个模型看不出自己的错。** 坑：两个 agent 跑的是同一个模型时，一个读另一个的 diff，看不出问题。现在：用不需要判断的检查补：逐个声明比对、DOM 或帧哈希、故意埋入、测试必须抓到的变异。
- **同一个操作实现了几遍。** 坑：同一个操作在几处各写一遍，改的时候总漏一处，几处慢慢各自漂移。现在：一个操作只留一份实现。

## 4. 多会话和 Git

- **宽路径 add 提交了别人的改动。** 坑：几个会话共用一个工作区时，`git add -A` 把别的会话还没做完的改动一起提交了。现在：按精确路径 add；收尾前跑 `git status`，标出哪些不是本会话的改动，不碰它们。

## 5. 长工程

- **一个阶段，一个会话。** 长项目切成阶段。阶段末把工作合并，会话停下，交一张架构图和完成情况；下一个会话先确认这个状态再动手。在哪停由人说。
- **撞了用量上限，从头再来。** 坑：中间结论只在上下文里，会话撞了用量上限，下一个会话只能从头做。现在：计划文件写成操作手册：原则、任务书模板、主 agent 维护的进度表、已经做出的决定、冷启动从哪开始；中间结论及时写进去。
- **思考强度按环节开。** 规划、拆任务、找根因、做审查时开到最高档（各家叫法不同：max、xhigh 之类）：这几步错了，后面每一步都跟着错。照着计划执行时 high 就够：难的判断已经在计划里做完，再开最高档主要是更慢、更贵。执行中冒出计划没覆盖的大判断，停下来拿回规划这一档去定，不在执行档里硬想。

## 6. 指挥 agent 的几个习惯

契约模板里已经有「问还是做」「拍板」「证据和汇报」的规则，这里只记模板里没有的：

- **需求分两栏**：功能性和非功能性，在任何设计之前拆好。工期不是砍掉其中一项的理由。
- **「我们是不是已经具备 X 需要的条件？」要的是差距清单**：已有什么、缺什么、改动多大，而不是直接开干。
- **主线先做完。** 中途冒出来的支线先记下、排队，除非人把它提前。

## 7. 审查和上下文隔离

- **审查换一双没看过的眼睛。** 计划或改动定稿前，交给一个没参与过的审查者：新会话、新的子 agent，最好是另一家的模型。审查者的任务书写清审什么、对照什么（计划文件、契约里的不变量）、每条意见什么格式（位置、怎么触发、多严重、几成把握）。
- **给材料，不给结论。** 问「哪里会坏」，不问「这样对不对」。把自己的判断递过去，审查者多半会顺着说。
- **意见是线索，不是结论。** 每条都由主 agent 复现或读代码核实，再决定改不改。核实不了的单独列给人，不悄悄丢掉。
- **给人看的文字像代码一样检查。** 坑：交付的报告读起来像机器写的。现在：报告、界面文字、README、对外材料交付前，交给一个完全没有背景的模型读：只给成品和读者是谁，不给对话、资料和自评。让它指出哪里读不懂、哪里像机器写的、哪个说法它会追问。它读不懂的，真读者也读不懂：改成品，不给它补背景。数字和事实盲读查不出来，另外逐条对回出处。
- **上下文会带偏判断。** 读过你推理过程的 agent 会顺着你的推理走；看过方案 A 的，很难公平地评方案 B。要独立的判断，就刻意不让它看到这些。
- **隔离观点，不隔离事实。** 约束、红线、文件在哪、什么算完成，写全；你的猜测、倾向、上一轮的结论，不给。子 agent 只知道任务书里写的，事实漏了它就自己猜。
- **隔离也护着主会话。** 大范围搜索、要读一堆文件的活交给子 agent，主会话只收结论，不收翻文件的过程。

## 8. 并行子 agent

- **互不依赖的活一起发。** 大范围搜代码、几份资料分头调研、同一份改动按几个角度分头审（正确性、安全、文档和代码对不对得上）：彼此不等结果，就同时派出去。
- **写文件的另算。** 两个写手不碰同一批文件；要并行写，每个写手一个工作树。后一步要用前一步结果的，按顺序做。
- **每个子 agent 一份自足的任务书。** 一个能检验的目标；只要结论，不要过程。
- **收回来逐份核。** 子 agent 的结论是要核的线索；几份审查意见先合并去重，再核。
- **并行是拿钱换时间。** 开几个子 agent，大约就花几份的钱。几次工具调用能做完的事，自己做。

## 9. 个人习惯跟着人走

- **个人习惯写在用户级的全局指令里。** 回复用什么语言、要图还是要文字、汇报什么格式、要不要它直说反对意见，这些跟着人走，不跟着项目走：写进 Claude Code 的 `~/.claude/CLAUDE.md`、Codex 的 `~/.codex/AGENTS.md` 这类用户级文件，每个项目都生效。项目契约只放这个项目的规则，两边冲突时以项目为准。换一台机器，先把这个文件带过去。
- **规则用什么语言写，agent 就容易用什么语言答。** 坑：skill 和契约全是英文，回答也跟着变成英文。现在：想要中文回答，就用中文版的 skill 和契约，并写明「一律用中文回复」。
- **想要图，就说「可视化」。** 讲结构、链路、现状，图比大段文字好懂。在带画图工具的客户端里（比如 Claude 桌面版），直接说「可视化」或「visualize」最容易让它真画出来；没有画图工具的环境，就要一页 HTML 报告或一张 Mermaid 图。
