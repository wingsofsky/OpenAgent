# 用文档保存项目上下文

新开的 agent 会话只知道它读到的文件。这个 skill 规定那些文件是什么：说明性文档放在 `docs/` 下固定的位置，另有三个文件装着每个会话都要先读的东西。

**用中文回复用户**，包括中途进度和收尾汇报；代码、命令、路径、标识符保持原样。

| 文件 | 装什么 |
|---|---|
| `CLAUDE.md` / `AGENTS.md` | 项目契约：每个会话都要遵守的规则，每条标出处，150 行以内 |
| `DECISIONS.md` | 每个设计选择，附证据和拍板人；只追加，不改旧条目 |
| `MEMORY.md` | agent 的长期事实索引：用户的偏好、本机的坑、东西在哪 |

进度写在 `docs/plans/`，不进这三个文件。

## 找文档

需要以前的计划、报告、决策或笔记时，以及每次写新文档之前：

1. **先看项目指向哪里。** 契约（`CLAUDE.md`、`AGENTS.md`）里常有「去哪找」一节，有的项目还有索引（`INDEX.md`、`docs/README.md`）。先照它们找；它们优先于下面几步。
2. **否则去对应的 `docs/` 分类里找。** 文件名以日期开头，按名字排序就是从旧到新：先读最新的，旧的当历史看。
3. **下「没有」的结论之前先搜**：先在文件名里搜主题词，再在正文里搜（`grep -ril <词> docs/`）。
4. **文档描述的是它写成那天的情况。** 依赖它之前，对一下代码、`git log` 或更新的文档；看到「已被取代」「已过时」的标注，就顺着找到替代它的那份。
5. **找到同一件事的文档，就更新它**，不要另起新文件。

## 存文档

新建说明性文档（报告、计划、调研或读书笔记、指南、审阅、清单），且同一件事还没有文档时：

1. 放在项目的 `docs/` 下对应的分类文件夹里，没有就建：
   - `docs/reports/`：工作报告、收尾、复盘
   - `docs/plans/`：计划、设计、路线图
   - `docs/research/`：调研、对比、论文或书的笔记
   - `docs/guides/`：使用说明、操作步骤
   - 拿不准：`docs/notes/`
2. 命名为 `YYYY-MM-DD-<主题>.md`，按日期排序，也能按名字找到主题。
3. **绝不**放在项目根目录、代码目录（`src/` 之类）或临时新造的顶层文件夹里。
4. 项目自己的契约对文档另有规定时，以契约为准。

文档怎么写不归这条规则管；它只需要能独立读懂（标题说清是什么、什么时候、关于谁）。

## 搭建契约、决策日志和记忆

用户要搭建或整理这些文件，或者项目还没有、用户同意建的时候：

- **契约**：从 [references/contract-template.md](references/contract-template.md) 起步。按你对项目和用户的了解填一份草稿给用户看；用户点头后再写 `CLAUDE.md`。项目还需要 `AGENTS.md`（Codex 等读这个名字）时，做成指向 `CLAUDE.md` 的链接或一行指引，绝不复制第二份。
- **决策日志**：从 [references/decision-log-template.md](references/decision-log-template.md) 起步。每个架构级选择一条，新的在前，只追加，每条写明谁拍的板。用户采纳的推荐就记成「推荐、用户同意」，绝不记成用户自己的决定。
- **记忆**：`MEMORY.md` 是索引，每条一行，细节放单独的文件。反复出现的偏好，提议升进契约。
- **每条规则都标出处**：`[owner]` 是用户的原话，`[agreed]` 是用户同意了的建议，`[incident]` 是返工得来的教训，`[D0xx]` 是决策日志条目。

这些习惯怎么来的，以及配套的协作做法（审查、上下文隔离、并行子 agent、思考强度、个人习惯放哪）：[references/working-with-ai-agents.md](references/working-with-ai-agents.md)。用户问到这些时先读它。

## 给项目做体检

用户要给项目的文档做体检，或者同意了安装后提议的体检时使用。先交报告；用户点头前，不移动、不写入任何文件。

1. **看现状。** 说明性文档现在放在哪（`git ls-files '*.md'`）；`CLAUDE.md` / `AGENTS.md`：有多长，里面有没有进度和状态行，有没有代码里已经对不上的说法，`AGENTS.md` 是不是一份走了样的副本；有没有决策日志（`DECISIONS.md`、`adr/`、`docs/adr/`）；提交规范是什么（`git log --oneline -30`、`CONTRIBUTING.md`、commitlint 之类）。
2. **交报告**，每条发现附证据（路径或命令输出），问用户下面两步要做哪一步。
3. **整理文档。** 逐个列出文件、它在 `docs/` 下的目标位置和以日期开头的新名字；契约里已有的约定优先。用户同意后用 `git mv` 移动，并修好指向它们的链接。
4. **重写契约。** 先收集素材：
   - 现有契约，每一行对照仓库核一遍；
   - 用户反复说过的话：装了 OpenAgent 的 sessions 模块的话，导入时加 `--prompts` 会在档案的 `_prompts/` 下写出 `USER_PROMPTS.md` 和 `USER_RULES.md`。一条规则要有两处以上用户说过的原话，按原样引用；
   - 用户自己的经验：问他们经常纠正什么、以前出过什么问题；
   - 第 1 步查到的提交规范。

   逐条判定：留在契约里（会改变 agent 的做法、从代码里看不出来、写错了代价高）；删掉（模型本来就会做、代码里看得出来、已经过时）；或者搬走（决策进 `DECISIONS.md`，进度进 `docs/plans/`，还没定下来的偏好进记忆）。按[契约模板](references/contract-template.md)起草，150 行以内，每条规则标出处。你自己推断出来的规则单独列出，逐条问用户要不要。
5. **交付。** 在聊天里贴出完整草稿，附上删了什么、为什么删。用户同意后才替换文件；`AGENTS.md` 如果是指向 `CLAUDE.md` 的链接或一行指引，保持原样。

## 不要做的事

- 不往契约里写进度、状态行或历史。
- 不先给用户看草稿，就不改他们的 `CLAUDE.md` 或 `AGENTS.md`。
- 不把决策日志的旧条目改成另一个意思；推翻就新开一条。
- 同一件事已有文档时，不另建新文档。
