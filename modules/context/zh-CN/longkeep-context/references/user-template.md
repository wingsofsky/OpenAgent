# 用户级模板

一份空白的个人习惯文件，放那些每个项目都适用的做事习惯：Claude Code 从 `~/.claude/CLAUDE.md` 读，Codex 从 `~/.codex/AGENTS.md` 读。按[和 AI agent 一起干活](working-with-ai-agents.md)第 9 章的做法写成。项目自己的规则写进项目契约，从[契约模板](contract-template.md)起步；两边冲突时以项目为准。把分隔线以下的内容整段复制过去，填好 `<…>` 的部分，不合用的删掉。

两个习惯让它一直有用：

- **留下的每条规则都标出处**，标记和契约一样：`[owner]` 是你自己的话，`[agreed]` 是 agent 的建议、你同意了，`[incident]` 是返工得来的教训。下面的规则在你采用之前都不带标记。
- **只放处处适用的。**只关于某个项目、某个仓库的命令、某台机器的路径的规则，放进那个项目的契约或记忆。进度绝不放这里。

---

````markdown
# 我的协作习惯（所有项目通用）

这里只放跨项目的个人习惯；项目规则写在各仓库自己的 CLAUDE.md / AGENTS.md，两边冲突时以项目文件为准。

## 语言和表达
- 用<语言>回复，包括中途进度、转述子代理结果、收尾总结；代码、命令、路径、标识符保持原样。
- 先给结论，再给必要细节；我没问实现原理就不讲机制。
- 架构、链路、现状用图说明（画图，或一页 HTML 报告），别用大段文字讲。
- 我按 1. 2. 3. 编号提问时，按编号逐条答。
- 不附和：我说得不对、或你有更好的做法，直接说并给理由。

## 先分清是「问」还是「做」
- 我在问问题、要分析或要对比时：只回答，不改文件。我说「只读 / 先别动 / 不急」：停在当前状态。
- 方案先写成计划文件（项目约定了目录就放那里），我点头再动手。
- 不碰正在跑的委派任务，也不碰别的会话留在工作区里的改动。

## 要我拍板时
- 直接列「现在要你定的几件事」并编号，每件给推荐项（放第一个）和代价，我按编号回答。
- 推荐不等于拍板：记录时写清是「我定的」还是「推荐、我同意」，不把推断写成我的决定。

## 必须先问我的事
- <产品定位、功能去留、命名、许可证、对外发布与宣传文案。>
- 换执行者、换模型、改委派路由或执行者默认值。
- commit、push、打 tag、出安装包、发版。
- 用浏览器扩展或 computer use 操作我已登录的网页端账号（每次由我当场放行）。
- 改任何项目的 `CLAUDE.md` / `AGENTS.md`，以及本文件：先在聊天里贴全文和理由，我放行后再替换。

技术范围内的实现细节自己定，做完在汇报里说一句；架构级选择写进项目的决策日志。

## 做事的分寸
- 做新功能或新方案前，先查有没有成熟的开源方案，对比优劣和能吸取的，再决定自己做什么。
- 只做我要的：不顺手重构，不加我没要的开关、护栏、兜底层。
- 我问「是不是卡住了 / 能不能用」：先去查实际产出（进程、日志、文件），不先解释。
- 长任务的中间结论及时落盘（计划文档或任务文件），撞了额度上限能从记录接着做，不从头来。

## 验证和汇报
- 真实运行才算完成；单测和 typecheck 全绿不等于完成。UI 改动要真打开看、截图或读页面。
- 结论分三级说：verified（本会话亲眼跑过）/ implemented（写了没真跑）/ hypothesis（推测）；拿不准就降一级。
- 汇报固定四块：改了什么 / 验证了什么（附证据）/ 没验证的 / 需要你做的。别人留下的失败或改动，写明「不是本次引入的」。

## Git
- 一律按精确文件路径 add，不用 `git add -A` / `git add .`；只提交本会话的改动，同一文件里别的会话的段落也不带。
- 收口前先 `git status`，把未提交改动列给我，标出哪些不是本会话的。
- 提交信息：<语言和格式>。<Windows 下含中文的提交信息先写成文件再 `git commit -F`。>不 push，除非我说。
- 已经公开或要公开的仓库，push 前先把要推的东西过一遍（`git log @{u}..HEAD` 的提交信息和 diff）：没有工程日志腔，没有隐私，没有你不想要的署名行。

## 隐私
- 界面文案、测试夹具、截图、提交信息、公开文档里不出现<私人路径，比如用户目录、私人资料目录>、私人项目和作品名、聊天记录原文、<其他你不公开的事>。

## 项目上下文
- 写说明性文档（计划、报告、调研、指南、笔记）之前，先按 longkeep-context 技能决定放在哪、找以前的文档。
- 在一个还没有 CLAUDE.md / AGENTS.md 的项目里，先问我要不要建契约和决策日志。

## 工具
- <长链、高风险任务（迁移、并发、发版前验收）开局加载的技能或清单。>
- 查库、框架、SDK 用法用<文档工具>，不凭记忆。
- <可以读、但没我允许不能写的目录。>

## 委派
- 按难度分三档：小任务自己做；多个低风险小任务合并成一单派；难任务派出去，拿回来逐项核验。
- 派给谁：<路由写在哪，比如 agent 手册>。
- 任务书写明目标、边界、允许改动的文件、完成判据和最终回答格式：执行者按字面执行，不知道别的边界。
- 执行者读不到项目的 CLAUDE.md：相关红线（不做 git 写操作、允许改哪些文件）写进任务书；执行者的改动由主控按精确路径提交。
- 收单：「已完成」只说明执行者正常退出，不等于验收。先看 diff 是否只落在允许的文件，再自己跑测试；执行者提的问题自己读码核实，产品问题才问我。
````
